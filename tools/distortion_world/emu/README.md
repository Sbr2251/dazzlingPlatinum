# DW headless kit (`tools/distortion_world/emu/`)

The shared test kit every rift workstream uses. Library + solver +
regression runner + table validator.

| file | what |
|---|---|
| `dwlib.py` | enter any rift at its entry state, move on any surface, read surface/tile from RAM, replay solution strings, detect falls/catches/resets, read `gDwPuzzleDebug`, write labelled frame strips |
| `solver.py` | offline solver framework: BFS shortest solution, no-soft-lock proof, difficulty stats, per-rift target checks, worked examples per mechanic |
| `rifts_regress.py` | play every rift from entry to totem fight start (+ LT1 shadow-wall exit), one worker process per rift, report + frame strips |
| `dw_tables_check.py` | host check over every `dw_puzzle_<map>.c` table + actor table (see below) |
| `gen_debug_offsets.py` + `dw_debug_offsets.json` | `DwPuzzleDebug` field offsets from `build/main.nef` DWARF |

Run with the Python 3.9 venv (the 3.12 venv's desmume is broken):

```sh
SDL_VIDEODRIVER=dummy ~/.venvs/desmume39/bin/python tools/distortion_world/emu/solver.py
```

One `Emu` per process (py-desmume segfaults on a second `DeSmuME()`).

## Entry

Primary: overworld entry. The kit patches a copy of the battle-stage
save in the file (approach tile, pre-entry `VAR_ARC2_PROGRESS`, the
rift's hide flag cleared, story-true totem flags, and for talk-rifts
the rift object itself -- see below) and steps onto (Ravaged Path) or
talks to (the rest) the rift object. The game's own warp sequence runs
`OnTransition`, which activates the DW system. A Continue boot
straight into a DW map does **not** run `OnTransition`, so the DW
system stays inactive there (no jumps, the fall warp crashes); direct
boot (`DwSession.boot_rift`) is for tile/pixel checks only.

Talk-rifts need their object in the save: a Continue boot loads the
save's object list, and the base save predates the rifts, so the rift
object is missing. The kit zeroes the stale list and appends the rift
object (localID/gfx/flag/script/coords from the map's events JSON,
status fields copied from a working static entry in the base save).
Ravaged Path needs no object: its entry is a step-on coord event.

Rift approaches (`OVERWORLD_RIFTS` in `dwlib.py`):

| rift | approach | trigger |
|---|---|---|
| Ravaged Path | (19,50), walk up the stairs | step onto (19,45) |
| Eterna Forest | (84,37) facing south | A, then Yes |
| Route 214 | (726,665) facing north | A |
| Route 213 | (715,831) facing north | A |
| Lost Tower (both visits) | (11,3), walk corridor + ledge + maze to (5,8) | A facing east |

Arc 1 enters through the Lake Verity portal bg event: (32,23)
facing south, A, then Yes.

(19,45) sits at height 2 and the stairs raise the player. Teleporting
straight to (19,46) leaves the player at the wrong height and the rift
never triggers.

## Movement

One move is one `FACE_*` direction as pressed on the surface the
player stands on (`FACE_UP = 0, DOWN = 1, LEFT = 2, RIGHT = 3`, the
D-pad key of the same name). The step table is the stock one in
`src/unk_0205F180.c`: floor `UP (0,0,-1) DOWN (0,0,+1) LEFT (-1,0,0)
RIGHT (+1,0,0)`; west wall `UP (0,+1,0) DOWN (0,-1,0) LEFT (0,0,+1)
RIGHT (0,0,-1)`; east wall the same except `LEFT/RIGHT` flipped in
`z`; ceiling `UP (0,0,+1) DOWN (0,0,-1) LEFT (-1,0,0) RIGHT (+1,0,0)`.

Solution strings are space-separated letters (`U/D/L/R` for `FACE_*`,
`W` an alias for `U`, `A` taps A, `.` waits). `DwSession.step`
presses one direction, waits for the step, pumps any dialogue (the
message box is detected by the light-pixel fraction in the top-screen
band rows 140-175: 0.56 with a box, 0.00 without), gives scripted
pauses a grace period, and settles again so a late warp (fall, fold,
carry) is that step's outcome. Falls are detected by the debug
`fallCount` when engine-a is present, else by the player settling at
the entry/checkpoint when the step did not target that tile.

The player tile comes from RAM: `sFieldSystem -> playerAvatar (+0x3C)
-> mapObject (+0x30) -> x (+100), y (+104), z (+108)`, with `y/2` as
the game reports it. The chain is torn down during warps, so reads
tolerate `None` there. The surface prefers `gDwPuzzleDebug.surface`
and otherwise infers it from the tile (y 1 floor, y 10 ceiling,
else the rift's wall).

## `gDwPuzzleDebug`

Read through the xMAP symbol of the same build, using engine-a's
`include/overlay009/dw_puzzle.h` layout. Offsets live in
`dw_debug_offsets.json`, generated by `gen_debug_offsets.py` from
`build/main.nef` DWARF -- never hardcoded (the pre-merge reader went
stale past slideTarget when slideSteps and the ActorPos padding
landed). After any `DwPuzzleDebug` change, rebuild and re-run the
generator (`--check` fails on drift). `stoneStates[]` is `u8[8]`
(RESTING 0, FALLING 1, LANDED 2). If the symbol is absent
(pre-engine-a ROM) `debug()` returns `None`; the kit falls back to
tile inference. `gDwPuzzleTestMode` is the only live RAM write the
kit makes (engine-a's documented harness gate), read back after
writing. Note: a warp resets the test-mode gate to off; the harness
re-enables it after each warp when it needs the test table.

## Table validator

`tools/distortion_world/dw_tables_check.py` is a host check over
every `dw_puzzle_<map>.c` table (engine-a) plus the actor table
(engine-b): it compiles the table files themselves against the real
headers (same pattern as `dw_actors_test.c`) and enforces the
authoring rules -- count caps (groups 8, sigils 16, runes 8,
currents 16, checkpoints 8, group tiles 32, explicit tiles 32,
stones 4, pads 4, shadow lane 16, edges 4/stone, protected 8,
echo sigils 8), landing tiles never current tiles, landing-tile
overrides VOID-only, landing uniqueness, landing tiles in no group
and never sigil / pad / checkpoint / rune tiles, stone starts /
edges never on protected tiles (no exemptions: a start may not sit
on another stone's landing), pads never checkpoint/rune/current,
shadow lanes never checkpoint tiles, on one surface, with
consecutive tiles adjacent (a jump teleports across a seam corner),
sigil targets in range, echo mirrorAxis != echoAxis (geometric
mapping), and for production tables (testOnly == 0): explicit
states for ground actor tiles, shadow beat >= 30 frames, and every
pad tile has a sigil in the engine-a table. Test tables are exempt
from the production-only rules. Pairs come from the engine
registry (`dw_puzzle.c` sPuzzleTables / sActorTables, by index)
first, then same-file pairing, then the known test pair. Only
fixture tables exist so far (Phase 2 has not written production
tables yet) -- the validator covers every table in the tree.
Totem/talk spots are map scripts, not tables, so they need
map-script review; the validator says so when it cannot see them.
Run it before committing a table change.

## Solver

`solver.py` is pure Python (no emulator). A model is surfaces (grids
per surface), jumps (edge jumps / hop points), start, goal, and
mechanics: `Sigils` (toggle/set/momentary/reset), `Runes`, `Currents`
(slides), `Stones` (push, drop to the surface below, plug currents,
protected push targets -- protected tiles are player-walkable, only
stone pushes are blocked), `Crumbling` (per-tile one-use),
`ScarGroups` (the Ravaged Path scars' exact rule), `Shadow`
(patrol lane, loop or ping-pong, WAIT `.` beats), `Echo` (mirror
ghost pressing its own sigils), plus `gate_tiles` (a tile walkable
only while its group is on).

It BFSes the shortest solution (pressed moves only; a current slide
is part of the one press that started it), proves no reachable
soft-lock IN THE MODEL (every reachable state can still reach the
goal over the model's transition graph, falls/resets included),
and prints difficulty stats: optimal length, branching (mean
out-degree over reachable states), required toggles/pushes, and
wrong-looking right moves (optimal steps that do not strictly
decrease the plain-grid distance to the goal).
`check_targets(rift, stats)` flags an optimal length outside the
revised PUZZLE_PLAN section 2 range, and a branching below the 1.2
harness floor for difficulty >= 2 (the plan gives no branching
ranges; the floor is a harness heuristic).

The proof is exact over the model, so the model's fidelity is the
workstream's responsibility: stones distinguish RESTING (BLOCKED,
pushable, plugs currents) from LANDED (SOLID walkable terrain,
unpushable, a slide passes over it); pushes follow the engine's
order (a designated edge drops before any walkability check; a
plain push is blocked on a protected tile, a stone, a non-walkable
tile, or a VOID tile); checkpoints snapshot groups, stones, shadow
phase + direction, and landed stones (momentary holders are
per-occupant and cleared on restore; a reset sigil's restore wins
over the same press's shadow tick); stone falls are atomic within
a press (the engine falls a stone over 12 frames, reserving its
edge and landing, but a step takes longer, so the reservation
lifts before the next press's push hook runs). Pads are not
modelled: they carry padUsed (one use per load per pad,
checkpointed and restored), which gates the totem-act
prompt/cutscene, not movement. A rift ships its model with its
tables, and the replay of the solver's solution on the ROM is the
cross-check that model and engine agree.

Worked examples: one per mechanic, plus `ravaged_path_model()`, a
sanity model of today's Ravaged Path wall that reproduces a 16-move
optimum (the solver's line steps once on the (y3, z21) scar tile --
legal, a scar holds exactly once -- as does the documented line).
Per-rift models ship with the Phase-2 tables (this kit provides the
framework + the Ravaged Path sanity model); `solver.py` exits 1 on
unsolvable models, soft-locks, or target violations.
