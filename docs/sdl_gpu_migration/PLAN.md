# Renderer migration: OpenGL to the SDL3 GPU API

Status: **in progress, wave 1 unfinished** (2026-11-12). This document is the handoff: it lets a new group of agents
resume every workstream. Read it fully before starting; then read `briefs/COMMON.md` and your workstream's brief.

## Why

The game now targets PC and, later, phones (CLAUDE.md, "Target: the Mac app"). The simulator (`subprojects/libntr`)
renders with OpenGL 4.1, which iOS does not have and Android only has as GLES. The owner chose the **SDL3 GPU API**
(`SDL_gpu.h`): one renderer that runs on Metal (macOS, iOS) and Vulkan (Windows, Linux, Android). A graphics overhaul
(lighting, shadows, widescreen) will be built on top of it afterwards, so the result has to be clean to extend.

## Decisions already made

| Decision | Choice | Reason |
|---|---|---|
| Graphics API | SDL3 GPU API | Metal + Vulkan from one codebase; SDL3 is already the platform library underneath `sdl2-compat` |
| Platform library | Real SDL3 (not `sdl2-compat`) | SDL3 GPU headers cannot be mixed with SDL2 headers |
| Shaders | Authored once in GLSL 450, compiled offline to SPIR-V (`glslangValidator`), cross-compiled to MSL (`spirv-cross`), embedded in the binary | The existing shaders are GLSL, so the DS-emulation shader logic ports with few changes; no HLSL/DXC dependency; no runtime shader compiler on phones |
| OpenGL renderer | Kept behind a startup switch `SIM_RENDERER=gl\|gpu` until the GPU renderer is proven equal | A/B frame comparison against GL is how the port is verified |
| `nx` / `prospero` targets | Not kept building | This project does not ship them; they would need SDL2 and SDL3 code side by side |
| Where simulator changes live | `tools/macos/patches/libntr.patch`, regenerated by the integrator at the end | Existing project convention (CLAUDE.md). During the work each workstream commits on a local branch inside `subprojects/libntr` |

## How the renderer works today (what is being replaced)

All in `subprojects/libntr/libraries/sim/src` unless noted. `g3_handler.cpp` and `g3_draw.cpp` are not compiled.

- **3D.** The game thread issues DS 3D commands all through the frame. `sim_g3_CommandProcessor.cpp` /
  `sim_g3_GlobalState.cpp` turn them into `DrawCall` objects; `sim_g3_GlRenderer.cpp` draws each one immediately
  into an offscreen framebuffer at internal resolution (256x192 times a scale, default 4), setting cull mode, depth
  function (`LESS` or `EQUAL`) and depth write per draw. Translucent draw calls are deferred to the end of the frame.
  The framebuffer stays bound "ambiently" between frames. Textures: `sim_g3_Texture.cpp`, `sim_g3_TextureCache.cpp`.
  One shader pair (`shaders/g3_*.glsl`) with fog tables (two 32-float arrays) and a polygon-mode switch.
- **2D.** At vblank `SIM_Render` (`sim_main.cpp`) composites each DS screen with `DrawEngine`: either the CPU 2D
  renderer (`sim_g2.cpp` rasterises BG/OBJ layers to RGBA textures, `shaders/g2_*.glsl` blends them with the DS
  blend/window registers) or the GPU 2D renderer (`sim_g2_gpu.cpp`, `shaders/g2gpu_*.glsl`: VRAM, OAM and palettes
  uploaded as integer textures, the shader decodes tiles with `texelFetch`). BG0 can be the 3D colour target.
  `SIM_G2_GPU=0|1` picks the path; both must keep working.
- **Post pass.** Both screens are composited into an offscreen frame; `shaders/post_*.glsl` draws it to the window
  with the PostFX effects that game code triggers through `include/port/postfx.h` (docs/postfx.md).
- **Overlay and present.** Dear ImGui (vendored, "1.93.0 WIP") with the SDL2 + OpenGL3 backends, then swap.
- **Readback.** `glReadPixels` of the back buffer in `SIM_DebugFrame` (`sim_main.cpp`), `sim_headless.cpp` and
  `sim_headless_control.cpp` (screenshots, the lockstep `screenshot` command, a centre-of-frame probe).
- **SDL use beyond the renderer.** Threads, mutexes, semaphores, timers and message queues in `libraries/os` and
  `include/nitro/os/common/*.h` (headers the whole game includes), audio in `sim_audio.cpp`, input and the event
  loop in `sim_main.cpp`, three files in `subprojects/libntrwifi`, and `src/port/sim_icon.cpp`,
  `src/port/savedata_upgrade.c` in the game.

The SDL GPU model differs in ways that shape the design: no global state; draws are recorded inside render passes
on explicit targets; cull/depth/blend state is baked into pipeline objects; uniforms are pushed as byte blocks per
draw; texture uploads happen in copy passes that cannot run inside a render pass; readback is a download plus a
wait; the swapchain may be BGRA. So the 3D draws issued during the frame must be recorded and replayed at frame end,
and every draw must carry its full state.

## Environment (cloud container, Ubuntu 24.04, 4 cores, no GPU)


- `setup_env.sh` installs the toolchain, builds SDL 3.4.20 into `../deps/prefix`, downloads the subprojects (with a
  workaround for the blocked wrapdb host), applies the project patches and creates the local branch `dazzling` in
  `subprojects/libntr`. Its skip-if-done path was run here; the from-scratch path is the same commands that were run
  by hand, not re-run end to end.
- `build_linux.sh` builds `build_linux/main`: about 14,000 steps, 35 minutes on 4 cores the first time.
- OpenGL runs on Mesa llvmpipe through SDL's offscreen/EGL driver; Vulkan runs on Mesa lavapipe (Vulkan 1.4).
  **Metal cannot be run here.** The Mac build has to be checked on the owner's machine.
- Parallel workstreams each need their own copy of the repo with its own build directory. A meson build directory
  only works at the path it was configured for, so `make_tree.sh <name>` copies the repo (about 3 GB) and
  `wt_run.sh <name> <cmd>` runs a command with that copy mounted over the repo path. After the first full build, a
  workstream that only touches simulator sources rebuilds in a minute or two.
- Budget: on this account, four agents (two Opus, two Sonnet) used a full 5-hour usage window without finishing
  wave 1. Plan for several windows, and have agents commit often.

## Verification method

1. **Lockstep A/B is the proof.** In lockstep mode (`SIM_CONTROL=stdio`, docs/headless_protocol.md) game state is a
   pure function of the save, seed, RTC and command stream, and the `screenshot` command captures the rendered
   frame. Checked here: two reference runs give byte-identical screenshots and identical protocol replies. Example:
   ```bash
   cd build_linux && printf '{"cmd":"step","frames":400}\n{"cmd":"screenshot","path":"/tmp/a.bmp"}\n{"cmd":"quit"}\n' | SIM_CONTROL=stdio SIM_SEED=12345 SIM_FIXED_RTC=2026-01-01T12:00:00 SIM_SAVE_PATH=/tmp/save.bin ./main
   ```
2. **Do not use `SIM_DEBUG_SHOT_EVERY` for A/B.** Its frame numbers are the DS vblank counter, which runs ahead of
   rendered frames at uncapped speed. Checked here: two identical reference runs produced 7 and 6 screenshots, and 5
   of the shared frames differed. (The first version of the briefs asked for this method; that was a mistake.)
3. **Compare pixels, not file bytes.** SDL3's BMP writer emits a different header (pixel data at offset 138, not
   122), so an SDL2 build and an SDL3 build never match by md5 even with identical pixels.
4. **Scenario suite:** `python3 tools/dazzling/test/run.py --game build_linux/main -j 1 --filter core_title` (75 s)
   and `--filter core_new_game` (about 5 minutes). Both pass on the OpenGL reference here. The other 25 scenarios
   skip: their save files exist only on the owner's Mac. Coverage here is therefore thin, which is why workstream 1d
   (comparison tours from a fresh game) matters.
5. Known reference behaviour on this machine: the CPU 2D and GPU 2D renderers give identical pixels at frames 401
   and 901 of a fresh boot.

## Open risks

- **Metal is untested until the owner runs it.** The MSL generation and binding mapping are the likeliest silent
  failure.
- **Thin automated coverage here**: two scenarios plus whatever tours 1d reaches. Battles, most field maps and menus
  are only covered if the tours get there.
- **Pixel-exactness**: OpenGL (llvmpipe) and Vulkan (lavapipe) rasterise edges and filter differently. The 3D layer
  will differ by small amounts at polygon edges; 2D and post should be exact or near it.
- **The simulator patch becomes a fork in practice**: after this migration, pulling upstream libntr renderer fixes is
  manual.
- **Simulator fixes found along the way** (already in `libntr.patch`, verified on Linux only): a register-block
  `memcpy` that aborted under Ubuntu's `_FORTIFY_SOURCE=3`, and a GPU 2D shader variable named `packed`, which Mesa
  reserves, so the GPU 2D path silently fell back to CPU on Linux.
